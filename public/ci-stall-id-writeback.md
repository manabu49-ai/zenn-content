記事を push すると自動で投稿される仕組みを作って、しばらく使っていました。

```
リポジトリに .md を置いて push
  → GitHub Actions
  → CLI が記事を投稿し、返ってきた記事IDをファイルへ書き戻して commit
```

よくある形です。書いて push するだけで公開まで終わる。実際、しばらくはそのとおりに動いていました。

## 6日ぶりに push して気づいた

新しい記事を1本足して push しました。そのあと、書き戻されるはずの記事IDを見に行ったら、`id: null` のままでした。

Actions の実行履歴を開きました。

```
Run 17  成功
Run 16  失敗   ← 今回
Run 15  失敗   ← 6日前
```

**6日前から失敗し続けていました。**その間に push した記事は、公開されていないと思い込んでいた——のですが、実際にはもっと悪い状態でした。

## エラー

```
{"message":"title has already been used. Please choose a different title.",
 "type":"unacceptable_entity"}
```

「その題名はもう使われている」。新規作成しようとして拒まれています。

しかし、拒まれた記事は**私が過去に投稿したもの**でした。更新するつもりのものが、新規作成として扱われていたことになります。

## 何が起きていたか

CLI は投稿に成功すると、記事IDをファイルに書き戻し、それを commit します。この書き戻しがあるから、次回は「更新」として扱われます。

```
1回目  id: null      → 新規作成 → IDが返る → ファイルへ書き戻して commit
2回目  id: xxxx...   → 更新
```

問題は、**この書き戻しの commit が、その実行で全記事の公開に成功したときしか作られない**ことでした。

```
記事A  成功  → IDが返る
記事B  失敗  → ここで exit 1
記事C  未処理
                ↑ 記事A のIDも書き戻されない
```

一度でも失敗すると、成功したぶんのIDまで失われます。IDが空のまま次に push すると、CLI はそれを新規作成として送り、サーバーが「その題名は既に使われている」と拒む。**また失敗する。**

```
IDが空 → 新規作成として送る → 題名の重複で拒否 → 失敗 → IDは書き戻されない → IDが空
```

**自分で自分を再生産する形になっていました。**外から直さないかぎり、何を push しても永久に公開されません。

私の場合、IDが空だったファイルは3本。うち2本は既に公開済みの記事でした。

## 気づけなかった理由

Actions の失敗通知はメールで届きます。届いていました。**読んでいませんでした。**

ただ、それだけではありません。この壊れ方には、症状が出ないという性質があります。

```
公開済みの記事  すでにサイト上にある。消えない
新しい記事      「まだ書いていないだけ」と区別がつかない
```

**サイトを見ても、壊れていることが分かりません。**過去の記事は並んでいるし、新しい記事が無いのは自分が書いていないからだと思える。実際、私は6日間ずっとそう思っていました。「更新が止まっているのは、書く時間を取れていないからだ」と。

書いていなかったのは事実です。しかし**書いても出なかった**ことには、押されるまで気づけませんでした。

## 直し方

サーバー側の公開APIから記事一覧を取り、題名が一致するものの記事IDをファイルへ書き戻すだけです。トークンは要りませんでした（公開記事の一覧は認証なしで取れる）。

```python
url = f"https://qiita.com/api/v2/users/{USER}/items?per_page=100"
with urllib.request.urlopen(url, timeout=30) as r:
    items = json.loads(r.read().decode("utf-8"))

by_title = {x["title"]: x["id"] for x in items}
# front matter の id が空なら、題名で引いて埋める
```

3本を埋めて push したところ、次の実行は成功しました。実測です。

そのうえで、**この処理を投稿の直後に必ず走らせる**ようにしました。書き戻しが失われても、次の実行までに自力で回復します。

```
push → Actions が投稿 → 90秒待つ → pull → IDを回収して書き戻す
```

## 残しておく教訓

**「状態をファイルに書き戻す」型の自動化は、書き戻しが失敗したときの姿を先に決めておく。**

書き戻しは、たいてい処理の最後にあります。最後にあるということは、途中で落ちたときに実行されないということです。そして状態が古いまま次の実行に入ると、同じ場所で同じように落ちます。

一度きりの失敗が、恒久的な停止に変わる。ここが分かれ目でした。

対処は難しくありません。**状態は、書き戻すのではなく、毎回サーバーから引き直せばよい。**サーバーが持っている状態こそが正であり、手元のファイルはその写しにすぎないからです。写しを正として扱ったことが、そもそもの間違いでした。
